# git 工作流命令参考

本文件只收集可复制的命令、失败恢复与回滚细节；**工序以 `steps/01`–`steps/09` 为准**，两者冲突时按步骤文件。为什么这样归一化、为什么远端只留必要分支，见 `knowledge/repository-hygiene.md`。

默认环境：Windows PowerShell 或 POSIX shell。命令按所在平台改写管道（`sort -u` 与 `Sort-Object -Unique` 等价）。

## 授权边界

- 用户没明确要求时：不 commit、不 push、不建 PR、不改 remote、不动分支。
- 用户要求提交时：只覆盖其列出的路径组与目标分支，不扩展到未列改动、`git add -A`、改 remote 或额外分支。
- 不 force-push 源码分支；不建空 commit；不删除远端分支，除非用户点名。
- 不用 `git commit --amend`（除非修复刚失败且未推送的提交）；不用 `-i` 交互式；不跳过 hooks；不更新 `git config`（除非明确要求）。
- 改写历史（rebase、filter、amend 已推送提交）需要用户显式授权；默认不做。

## 提交前

```bash
git status --short
git branch --show-current
git remote -v
git diff --stat
git log --oneline -10
```

只在任务确实涉及提交、变更总结、审查、冲突解决或发布说明时运行；普通文档、资料、分析和问答不需要例行对比。

确认：

- 当前分支是目标分支；不在 detached HEAD。
- 用户既有未提交改动没有被卷入本次范围。
- 远端地址指向预期仓库（`git remote -v`）。

## 显式暂存

```bash
git add path/one path/two
git diff --cached --stat
git diff --cached --check
```

- 禁止 `git add -A`、`git add .`；即使用户要求提交整个工作区，也先列清文件再逐个显式暂存。
- 二进制或大文件先确认是否该入库；生成物、缓存、本机配置应先进 `.gitignore`。
- 取消暂存用 `git restore --staged <path>`，不要用 `reset --hard`。

## 提交信息

结构、类型与扩展规则见 `steps/04-write-message.md`。摘要：

```text
type(scope): 中文说明
```

- `type` 取 `feat`、`fix`、`build`、`chore`、`ci`、`docs`、`style`、`refactor`、`perf`、`test`、`revert`。
- `scope` 可选，写小写 kebab-case；冒号必须是英文半角且后跟一个空格。
- 描述至少一个汉字、不超过 50 个字符、结尾不加句号；技术专名可保留英文。
- 破坏性变更在冒号前加 `!`，例如 `refactor(api)!: 移除旧入口`；`BREAKING CHANGE` 必须全大写。
- 提交前用 `git_commit_check` 检查完整信息；提交时用 `git commit -F <message-file>`，不要用 `-m` 重拼。

示例：

```text
docs: 补充术语表
refactor(agents): 索引目录并入单一配置
ci(pages): 发布前增加产物 smoke 检查
```

## 身份门禁

- commit 的 author 与 committer 都必须是项目声明的维护者本人；身份只从 `AGENTS.md`/`CONTRIBUTING.md` 读取，不从 `git config` 猜测。
- 提交前用 `git var GIT_AUTHOR_IDENT` 与 `git var GIT_COMMITTER_IDENT` 只读比对声明身份；不一致就停止，不用 `git config` 改配置，必要时经授权用一次性 `git -c user.name=... -c user.email=... commit`。
- 禁止把任何 AI 或第三方写进 `Co-authored-by:`、`Signed-off-by:` 等 trailer，也不得在提交说明正文署名；项目强制 DCO 时只允许维护者本人的 `Signed-off-by`，并通过 `allowed_trailers` 显式放行。
- 禁止关键字包括 `Cursor`、`cursoragent`、`Cursor Agent`、`Made with Cursor`、`Generated by Cursor`。
- 不要使用会自动追加 AI trailer 的 IDE 生成按钮。

只读人工核对：

```bash
git log --format='%an <%ae> | %cn <%ce>' -n 30 | sort -u
git log -n 30 --format='%(trailers:key=Co-authored-by)'
git log -n 50 --grep='Co-authored-by\|Cursor\|cursoragent\|Made.with Cursor' -i --oneline
git diff --cached --check
```

插件包自带脚本，默认检查下一次 push 的范围（不是全部历史），并调用与工具相同的规则：

```bash
node skills/shipping-github/scripts/checking-commit-identity.mjs \
  --author "Alice <alice@example.com>"
```

需要审计全部可达历史时才显式加 `--all`。项目已有等价脚本时用项目脚本，不要为同一门禁写两份。

## 推送

```bash
git fetch origin
git push origin HEAD
git ls-remote origin refs/heads/<branch>
git rev-parse HEAD
```

- 远端 SHA 必须与本地 `HEAD` 一致才算推送成功。
- 不要用 `git status -sb` 判断：没有 upstream tracking 时 ahead 信息不可靠。
- 推送被拒时先 `git fetch` 看远端是否前进；需要合并时用普通 merge；只对未推送的本地提交 rebase，不 force-push。
- 首次推送用 `git push -u origin main` 建立 tracking。

## PR 与 Issue（gh CLI）

```bash
gh pr create --base main --head <branch> --title "type(scope): 中文说明" --body-file <body.md>
gh pr checks --watch
gh pr view --web
gh issue create --title "<标题>" --body-file <body.md>
```

- PR 正文写：动机、改动面、验证方式、风险与回滚点。
- 等 checks 通过再合并；合并方式按项目约定（squash/merge/rebase），不擅自改变。
- Issue 写可复现步骤、期望结果、实际结果、环境；不贴密钥、令牌或完整个人路径。
- 没有 `gh` 或未认证时，报告并让用户选择网页操作，不擅自安装或登录。

## 大更新怎么分组

先看：

```bash
git status --short
git diff --stat
git diff --name-only
```

再按「出错时希望回滚到哪」分组，每组显式暂存并检查。没有固定提交数量；不为拆分而拆分，也不把不可运行的中间状态单独提交。范围不清楚就问，不猜。

## 回滚

```bash
git restore <file>             # 丢弃工作区改动
git restore --staged <file>    # 取消暂存
git reset --soft HEAD~1        # 撤销最近一次未推送 commit（保留改动）
git revert <sha>               # 已推送提交用反向提交回滚
```

- 不使用 `git reset --hard`，除非用户明确要求且确认没有未保存改动。
- 已推送历史只能追加 `revert`，不能改写。

## 首次上传（init → 建仓 → push）

```bash
git init -b main
git status --porcelain        # 先核对：无 node_modules、产物目录、缓存、本机配置
git add --renormalize path/one path/two
git status --porcelain
git commit -F <message-file>
```

建仓优先用托管端或 `gh repo create`；没有 `gh` 时在网页新建空仓库（不要勾选初始化 README/license），然后：

```bash
git remote add origin https://github.com/<owner>/<repo>.git
git push -u origin main
```

建仓前先把站点配置里的 `repo-url`、`site-url` 占位换成真实地址，避免二次提交。

## Git 对比频率

| 场景 | 是否需要频繁对比 |
| --- | --- |
| 写文档、查资料、数据分析、生成文案、普通问答 | 不需要 |
| Code Review、提交信息生成、变更总结、冲突解决、发布说明 | 需要，但通常只在执行时查一次或几次 |
| 调试「最近改动导致的问题」 | 可能需要，查最近 diff/log 即可 |
| 维护 skills 仓库本身 | 用 Git 管理即可，不必运行时频繁对比 |

执行 Git 操作前读取一次足够的状态即可。只有任务范围变化、出现冲突或验证失败时才重新检查。

## 失败恢复

- push 报 `Connection was reset` / 超时：先重试一次；仍失败再查网络、代理与 DNS，不要连续推空提交试错。固定 IP 只是临时手段，不写进仓库配置。
- 远端 404：先确认远端仓库是否真的存在（`gh repo view`、`git ls-remote`），不要把「本地有 commit」当成「远端已建仓」。
- 提交后才发现漏文件：未推送时 `git add` 后 `amend`；已推送时追加新提交，不改写历史。
- 门禁失败：先在本地复现并修因，不盲目追加 commit 触发 CI。

## 完成回报

按 `steps/09-ship-report.md` 调用一次 `git_ship_report`，回执写清模式、分支、提交、远端 SHA、四项检查和未做项。不要把「本地检查通过」说成「已发布」。
