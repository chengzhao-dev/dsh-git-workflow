# 公开面与发布内容划界依据

本文件回答「什么该上公开面、为什么」；门禁顺序与命令见 `references/publish-gate.md`，Pages 机制见 `pages-deployment.md`。

## 发布内容为什么这样划界

- 源码分支上公开的是未被 `.gitignore` 排除的项目文件；产物分支上只有自动化推上去的渲染结果。两者互不污染。
- 产物分支用孤立提交覆盖，产物不累积历史；代价是失去产物级回滚，只能回源码重渲染。
- 不进任何分支的条目各有归属：本机构建目录、渲染缓存、一次性产物、本地计划与临时区、编辑器个人配置。它们要么可重建，要么只对当前机器有意义。
- 公开面的判断标准是「换一台机器、换一个访问者，这条内容还成立吗」。本机路径、凭据、个人配置不成立；源码、构建说明、贡献指南成立。

## CI 覆盖到哪里

- CI 覆盖可以在干净环境里复现的检查：文档渲染、链接与编码、技能结构、单元测试、产物 smoke。
- 需要本机工具链、私有依赖或长时间构建的步骤，若 CI 无法稳定复现，就不要为了「看起来完整」硬塞进去；在贡献指南里写明本地必跑命令，发布检查以本地结果为准。
- CI 是复核，不是唯一门禁。本地检查通过、CI 通过、线上读回通过是三件不同的事，要分别报告。
- 工作流只授予实际步骤需要的权限；用不到的权限删掉，而不是留着「以后可能用」。

## 根入口文件的放置

- `.gitignore`、`.gitattributes`、`.editorconfig` 放仓库根：忽略与属性规则按所在目录向上生效，根上一份覆盖全仓；EditorConfig 从被打开文件向上查找，`root = true` 必须在任何节之前，放子目录盖不住其它目录。
- 贡献指南放仓库根，GitHub 只在仓库根、`docs/`、`.github/` 三处识别；若项目没有 `docs/`，就放根并让 README 链过去。
- 工作流放 `.github/workflows/`，复合动作放 `.github/actions/`；它们是平台约定路径，不要为了「目录整齐」挪走。
- 许可证、README 放根：托管平台与包管理器按固定位置读取。

## 本机配置与可复现配置

- 纯工具路径与版本清单可以入库，方便复现；密钥、token、可识别个人的主目录路径不入库。
- 本机配置要么放 `.git/info/exclude` 覆盖的个人文件，要么提交一份模板并让使用者复制为本地文件。
- 配置文件里出现绝对路径时，先问「别人 clone 后这条路径还有效吗」；无效就改成相对路径或环境变量。

## 公开面的风格约束

- 公开面一旦形成稳定风格（目录命名、文件命名、文档语气、代码风格），后续改动应维持而不是顺手重排；风格迁移的 diff 会淹没真实变更。
- 风格约束要有单一出处：要么在项目规范里，要么在工具配置里，不要两处各写一份而内容不同。
- 教学型或示例型仓库可以有意偏离通用规范，但偏离项要登记理由与适用范围；未登记的偏离会被后来者当成错误修掉。
- 新增公开面能力（PDF、多语言、搜索、评论）前先确认维护成本与现有风格是否兼容；不能维护的能力不加。

## 发布面与项目结构的关系

- 公开面只暴露项目结构的一部分：源码、文档、构建入口、贡献方式。内部计划、临时稿、实验分支不公开。
- 目录结构应让访问者能区分「这是什么」与「怎么用」；维护规则放在贡献指南或项目规范里，不塞进读者文档。
- 如果项目同时有源码与书/站点，产物目录名与源码目录名要能一眼区分，且产物目录被忽略。
- 非 git 的项目决策（代码风格、目录布局、框架选型）由项目自己的知识文件承载，不放进本技能；本技能只保留与发布边界相交的部分。
