# GitHub Pages 部署方式与产物分支策略

本文件记录站点发布环节的实际行为与取舍依据。可执行清单见 `references/github-pages.md`，不在此重复。

## 部署源的类型与边界

### 分支部署与工作流部署不可混用

1. Pages 只有两类部署源：读取仓库内某个目录的分支部署，和接收流水线上传产物的工作流部署。
2. 两者的步骤与权限要求不同，混用的表现是同时缺权限和多出无用配置，而不是报出明确错误。
3. 分支部署要同时核对分支与目录两项，任一项不匹配的表现都是「推送成功但页面不变」。
4. 希望产物在源码仓库里可见，就要把输出目录改到被分支读取的路径，代价是产物进入版本控制并放大 diff。

### 权限由部署方式决定

1. 需要哪些权限取决于谁在写产物：推分支需要写内容权限，走平台部署件还需要写页面与签发令牌权限。
2. 用不到的权限留在配置里不会报错，但会扩大令牌的可用范围，应当按实际步骤删减。
3. 凭据由平台在任务内临时签发，不写入仓库也不外传，这是发布链路不泄露密钥的前提。

## 产物分支策略

### 源码分支与产物分支分离

1. 产物推到独立分支后，站点端可以直接查看实际 HTML，源码历史不被生成物污染。
2. 每次部署用孤立提交覆盖产物分支，可阻止历史噪音累积，代价是失去产物级回滚，只能回到源码重渲染。
3. 产物分支只由自动化更新，手工把源码推上去会在下一次部署时被整体覆盖。
4. 分支保护分两类：禁止删除与禁止强推。源码分支两类都要，产物分支至少要禁止删除，否则站点会消失。

### 并发与排队

1. 同一时刻只允许一个部署任务，后来者排队而不是取消进行中的任务，否则产物分支可能停在半更新状态。
2. 「页面没变」的排查顺序固定为：先确认任务是否成功，再核对部署源配置，最后才考虑缓存与全球分发延迟。
3. 任务成功但页面未更新时不要重复触发部署，重复部署只会加深半更新风险。

## 站点路径与首次启用

### URL 前缀决定链接写法

1. 项目站点的地址带仓库名前缀，用户或组织站点不带，前缀变化会让写死的绝对地址全断。
2. 页面内资源一律用相对路径，由渲染器在生成时修正链接后缀。
3. 本地正常、线上 404 优先怀疑大小写：托管端区分大小写，本地文件系统通常不区分。
4. 章节导航与站点导航来源不同：Book 的章节顺序由章节列表决定，站点型导航由站点配置的导航栏与侧栏决定，混放会两边都不生效。

### 首次启用的幂等处理

1. 首次部署时部署源可能尚未设置，需要显式调用接口设置源。
2. 已配置过的仓库再次设置会返回冲突，这属于预期结果，可以继续而不是判定为失败。
3. 接口失败不等于部署失败，非致命告警必须留下可执行的人工处置提示，否则排查会停在猜测上。
4. 配置里的仓库地址与站点地址要在首次提交前换成真实值，否则产物里的链接指向不存在的站点，事后修正要重渲染全站。

## 发布验证的判定依据

### 渲染通过不等于可发布

1. 渲染成功只证明内容可解析，不证明链接可达。相对链接要在与线上一致的前缀下检查。
2. 单文件分发要显式开启内嵌选项，默认渲染仍会产出依赖目录，把目录一起上传才可用。
3. 示例代码的可编译性由独立校验保证，渲染成功不代表示例本身正确，两者是两条不同的检查。
4. 检查清单的每一项都要能对应一条命令或一个可观察结果，否则它只是提醒而不是验收标准。

### 验证代价与范围

1. 改动主题或全局配置会影响所有页面，增量检查无法覆盖，只有整站渲染能暴露问题。
2. 验证范围要与改动影响面对齐，影响面不明的最小改动宁可变宽也不可变窄。

## 延伸阅读

1. GitHub Pages 的部署源与权限说明决定流水线需要哪些权限，改配置前先查它。
2. 渲染与编码环节的失效模式由具体渲染工具的文档承担，不在本技能重复。
3. 具体项目的现行发布实现是项目级事实，改动前先读工作流文件而不是凭记忆重写。
